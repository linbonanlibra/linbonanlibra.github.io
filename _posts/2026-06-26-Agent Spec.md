# Agent Spec

> Agent 工程中的规格说明：从模型价值观到任务定义

---

## 一、Spec 是什么

在 Agent 工程里，"Spec"（Specification，规格/规范）有两层含义，经常被混用：

| 层次 | 含义 | 类比 |
|---|---|---|
| **Model Spec** | 定义模型本身的价值观、行为边界、优先级规则 | 公司的价值观手册 |
| **Task Spec** | 定义某个具体任务"什么叫做完成" | 产品的需求文档 |

两者都解决同一个核心问题：**如何让 Agent 知道该做什么、不该做什么、做到什么程度算成功。**

---

## 二、Anthropic Model Spec：模型的"宪法"

Anthropic 为 Claude 编写了一份公开的 **Model Spec**，定义了 Claude 的价值观、性格、优先级规则。这是 Agent 工程里最重要的"隐性规范"——即使你不写任何 system prompt，Claude 也已经按这套 Spec 在运作。

### 2.1 Principal 层级（指令优先级）

Claude 的所有行为都基于一个**三层 Principal 体系**：

```
┌─────────────────────────────────────────┐
│  Anthropic（最高优先级）                  │
│  通过训练写入模型，无法被覆盖              │
│  → 绝对红线（不能制作生化武器等）          │
├─────────────────────────────────────────┤
│  Operator（你，开发者）                   │
│  通过 system prompt 传达                  │
│  → 可以扩展/限制 Claude 默认行为          │
├─────────────────────────────────────────┤
│  User（终端用户）                         │
│  通过 messages 传达                       │
│  → 在 Operator 允许的范围内行动           │
└─────────────────────────────────────────┘
```

**关键含义：**

```
Operator 可以：
  ✅ 限制 Claude 的话题（"只讨论编程问题"）
  ✅ 赋予 Claude 特定角色（"你是一个法律顾问助手"）
  ✅ 允许 Claude 做默认不做的事（成人平台的内容）
  ✅ 限制用户修改 Claude 行为的能力

Operator 不能：
  ❌ 指示 Claude 欺骗用户损害用户利益
  ❌ 绕过 Anthropic 的训练红线
  ❌ 让 Claude 帮助实施违法行为

User 可以：
  ✅ 在 Operator 允许的范围内调整行为
  ✅ 声明自己的专业背景获得更专业的回答
  ✅ 选择对话风格、语言等偏好
```

### 2.2 硬编码 vs 软编码行为

Model Spec 将 Claude 的行为分为两类：

```
硬编码行为（Hardcoded / Locked）：
  无论任何指令，永远不做的事
  → 协助制造大规模杀伤性武器
  → 生成 CSAM
  → 帮助攻击关键基础设施
  → 当被追问时承认自己在假装是人类

软编码行为（Softcoded / Instructable）：
  默认行为，但可以被合理指令修改

  默认开启，Operator 可关闭：
    → 响应用户语言（非 system prompt 语言）
    → 提供安全危机建议
    → 保持政治中立

  默认关闭，Operator 可开启：
    → 生成成人内容（需平台资质）
    → 详细描述危险活动（需专业平台）
    → 扮演指定角色不出戏
```

### 2.3 对 Agent 工程的影响

理解这个层级，直接决定你的 system prompt 怎么写：

```
❌ 错误认知："我在 system prompt 里写了，Claude 就会无条件执行"

✅ 正确认知：
  system prompt 是 Operator 层的指令
  Claude 会遵守，但：
    1. 不能违反 Anthropic 训练的红线
    2. 不能让 Claude 反过来伤害用户
    3. 指令越具体清晰，Claude 越准确遵守
```

## 三、Task Spec：定义"完成"是什么

Task Spec 是告诉 Agent **"做什么"** 以及 **"做到什么程度算完成"** 的规格说明。

这是 Agent 工程里最容易被忽视、却影响最大的环节。

### 3.1 模糊 Spec vs 清晰 Spec

```
❌ 模糊 Spec：
  "帮我分析这份报告，写一份好的总结"
  问题：什么叫"好"？多长？什么格式？给谁看？

✅ 清晰 Spec：
  "分析这份 Q4 财报（PDF），面向董事会，
   输出一份 500 字以内的执行摘要，包含：
   ① 营收同比变化  ② 主要风险点（≤3条）  ③ 建议行动项
   格式：Markdown，无需图表"
```

**清晰 Spec 的五个要素：**

| 要素 | 问题 | 示例 |
|---|---|---|
| **目标** | 做什么？ | 分析 Q4 财报 |
| **受众** | 给谁看？ | 董事会 |
| **输出格式** | 什么形式？ | 500字 Markdown 摘要 |
| **成功标准** | 什么叫完成？ | 包含营收/风险/建议三项 |
| **约束条件** | 什么不能做？ | 无需图表 |

### 3.2 Rubric：可量化的完成标准

当任务交给 Agent 自主完成时，模糊的"好"是最大的敌人。**Rubric（评分标准）** 是将"好"量化为可检验条件的工具：

```markdown
# DCF 模型构建 Rubric

## 必须满足（缺一即失败）
- [ ] Excel 文件可以正常打开，无损坏
- [ ] 包含独立的 Assumptions 标签页
- [ ] 自由现金流预测覆盖 5 年
- [ ] 折现率（WACC）有计算过程，非硬编码

## 应当满足（影响质量评分）
- [ ] 使用历史数据作为预测基准（近 3 年）
- [ ] 敏感性分析：WACC ±1%，增长率 ±0.5%
- [ ] 所有假设有来源注释

## 加分项
- [ ] 包含 Monte Carlo 情景分析
- [ ] 图表可视化关键指标趋势
```

在 Claude Managed Agents 里，这个 Rubric 可以直接用于 **Outcome-graded 循环**：

```typescript
// 把 Rubric 交给 Agent，让它迭代直到满足标准
await client.beta.sessions.events.send(session.id, {
  events: [{
    type: "user.define_outcome",
    description: "为 Costco 构建 DCF 模型，输出为 .xlsx 文件",
    rubric: { type: "text", content: RUBRIC_MD },
    max_iterations: 5,  // 最多迭代 5 次
  }]
});

// Agent 自动：执行 → Grader 评分 → 不满足则修改 → 再评分 → 直到满足或超限
```

## 四、System Prompt 即 Spec 的实践

System prompt 是你向 Claude 传达 Task Spec 和行为 Spec 的主要渠道。写得好不好，直接决定 Agent 的质量。

### 4.1 System Prompt 的结构

```markdown
# [角色定义]
你是 Acme 公司的代码审查助手，专注于 Python 代码质量。

# [能力边界]
你只处理代码相关问题。用户问其他问题时，
礼貌地说明你只负责代码审查，并引导他们使用其他渠道。

# [行为规范]
审查代码时：
1. 先理解代码意图，再指出问题
2. 每个问题给出具体的修改建议
3. 按严重性排序：安全 > 性能 > 可读性

# [输出格式]
返回 Markdown 格式，包含：
- 问题列表（每条含：位置、描述、建议）
- 整体评分（1-5 分）
- 一句话总结

# [约束条件]
- 不评价代码风格（除非有安全影响）
- 不提供超出当前代码范围的重构建议
```

### 4.2 新旧模型对 Spec 理解的差异

**重要：Opus 4.7/4.8 等新模型对指令的遵守更精确，反而可能带来问题。**

```
旧模型的处理方式：
  "CRITICAL: 你必须使用搜索工具！" → 模型可能仍然不用（需要强调才会用）

新模型的处理方式：
  "CRITICAL: 你必须使用搜索工具！" → 每次都用，哪怕不需要（过度触发）
```

**Spec 写法的迁移：**

```
❌ 旧写法（针对旧模型不听话）：
  "CRITICAL: YOU MUST use the search tool for every question"
  "ALWAYS check the database before answering"
  "If in doubt, use the tool"

✅ 新写法（针对新模型精确遵守）：
  "当用户询问实时信息时，使用搜索工具"
  "如果答案依赖数据库中的数据，先查询数据库"
  "（删除）if in doubt 类的指令"
```

### 4.3 Spec 中的工具触发条件

对新模型来说，工具描述里的**触发条件**比工具名称更重要：

```typescript
// ❌ 模糊描述：模型不知道何时用
{
  name: "search_web",
  description: "搜索网络获取信息",
}

// ✅ 明确触发条件：模型知道"什么情况下必须调用"
{
  name: "search_web",
  description: `搜索网络获取最新信息。
    当以下情况时调用此工具：
    - 用户询问近期事件（2024年后）
    - 用户询问实时数据（股价、天气等）
    - 用户明确提到"最新"、"现在"、"今天"
    不需要调用的情况：
    - 问题基于用户提供的文档内容
    - 通用知识性问题（历史、原理等）`,
}
```

## 五、Spec 的可测试性

好的 Spec 必须是**可测试的**——你能写出测试用例来验证 Agent 是否符合 Spec。

### 5.1 测试用例矩阵

```
正向用例（应该做的）：
  ✅ 给定 Python 代码 → 应该返回审查结果
  ✅ 代码有 SQL 注入漏洞 → 应该标记为严重问题

边界用例（边界情况）：
  ✅ 给定空文件 → 应该说明没有问题或提示文件为空
  ✅ 代码超过 1000 行 → 应该正常处理而不是截断

负向用例（不应该做的）：
  ❌ 用户问"今天天气" → 不应该回答，应该引导到其他渠道
  ❌ 用户要求"帮我删除所有测试" → 应该拒绝或确认
```

### 5.2 Spec 变更的影响评估

当你修改 system prompt（即修改 Spec）时，需要重新测试：

```
修改了角色定义 → 测试所有正向用例
修改了约束条件 → 重点测试负向用例
修改了输出格式 → 测试格式符合预期
升级了基础模型 → 全量回归测试
```

## 六、Claude Code 自身的 Spec 体系

Claude Code 本身就是一个按严格 Spec 运作的 Agent，它的规格包含多个层次：

```
层次 1：Anthropic Model Spec（训练写入）
  → Claude 的价值观、安全边界

层次 2：Claude Code 系统提示（Anthropic 编写）
  → 如何处理代码任务、文件操作规范、确认机制

层次 3：CLAUDE.md（你编写）
  → 项目特定规范，Claude Code 每次启动自动读取
  → 例：测试命令、编码规范、目录结构约定

层次 4：当前对话中的指令（你实时给出）
  → 本次任务的具体要求
```

**CLAUDE.md 就是你为项目编写的 Spec：**

```markdown
# CLAUDE.md 示例

## 项目结构
src/api/       → API 路由层，不含业务逻辑
src/service/   → 业务逻辑层
src/repository/→ 数据访问层

## 开发规范
- 使用 TypeScript strict 模式
- 所有 API 返回值必须有类型定义
- 新增功能必须有对应单元测试

## 常用命令
- 运行测试：npm test
- 启动开发服务器：npm run dev
- 构建：npm run build

## 禁止操作
- 不直接修改 node_modules
- 不在 src/ 外创建业务代码文件
```

## 七、Spec 设计的常见陷阱

### 陷阱 1：Spec 过于宽泛

```
❌ "做一个好的助手，帮助用户解决问题"
   → Agent 不知道边界在哪，什么都做，什么都做不好

✅ "作为代码审查助手，专注于 Python 代码安全审查..."
```

### 陷阱 2：Spec 自相矛盾

```
❌ "始终简洁回答" + "提供完整的解释和背景"
   → Agent 不知道该简洁还是详细

✅ "默认简洁回答；用户明确要求详细解释时，再提供完整背景"
```

### 陷阱 3：把工程约束写成 Spec

```
❌ "你只能使用我提供的工具，不能超出范围"
   → Claude 本来就只能用你提供的工具，这是工程约束而非 Spec

✅ 直接不提供不需要的工具（让工程边界承担约束职责）
```

### 陷阱 4：Spec 无法验证

```
❌ "提供高质量的回答"
   → "高质量"无法测试

✅ "回答必须包含：① 直接答案 ② 至少一个代码示例 ③ 潜在风险提示"
   → 三个条件都可以程序化验证
```

## 八、Spec 的演化：从 Prompt 到 Outcome

Spec 的表达方式随 Agent 能力的增强而演化：

```
阶段 1：Prompt Engineering（命令式）
  "第一步做 X，然后做 Y，最后输出 Z 格式"
  → 适合简单任务，人来规划步骤

阶段 2：System Prompt（声明式）
  "你是一个 X 助手，遵守以下规范..."
  → 适合中等复杂度，定义角色和规范

阶段 3：Rubric + Outcome（目标式）
  "完成这个任务，满足以下评分标准，直到合格为止"
  → 适合复杂任务，定义目标而非路径
  → Agent 自主规划路径，系统评估结果
```

这个演化路径反映了一个核心转变：

> **从"告诉 Agent 怎么做"到"告诉 Agent 做到什么"**

## 总结

```
Spec 的两个层次：

Model Spec（模型层）
  → 由 Anthropic 定义，写入训练
  → 确立 Principal 层级：Anthropic > Operator > User
  → 定义硬编码（不可改）和软编码（可调整）行为
  → 影响：你的 system prompt 能做什么、做不到什么

Task Spec（任务层）
  → 由你定义，写在 system prompt / CLAUDE.md / Rubric
  → 定义角色、能力边界、成功标准、输出格式
  → 影响：Agent 在具体任务中的表现
```

**写好 Spec 的核心原则：**
1. 明确优先于模糊，可测试优于主观
2. 定义"完成"比定义"过程"更重要
3. 约束应该落在工程层（不提供工具），而非 Spec 层（"不许做"）
4. 随模型能力演化，Spec 从命令式走向目标式
