## 一、HSM：硬件安全模块

### 1.1 是什么

HSM（Hardware Security Module，硬件安全模块）是一种**专用的物理硬件设备**，专门用于在防篡改的安全环境中**生成、存储和使用密钥**。

核心原则：**密钥永远不会以明文形式离开这块硬件。**

### 1.2 为什么需要 HSM

软件密钥管理存在根本性缺陷：

```
密钥存在内存/磁盘中
  → 操作系统可以访问
  → 管理员可以 dump 内存
  → 恶意软件可以窃取
  → 密钥备份/迁移时会暴露
```

HSM 的解法是把密钥锁进一个**物理上无法读取明文的黑盒子**。

### 1.3 工作原理

#### 物理防篡改

| 攻击手段 | HSM 的对抗 |
|---|---|
| 打开外壳 | 检测到后自动清除密钥（zeroization） |
| 电压/温度攻击 | 传感器检测异常后自毁密钥 |
| 探针攻击总线 | 内存加密，物理线路混淆 |
| X 光扫描 | 内部结构不暴露密钥存储位置 |

#### 密钥的"不出境"原则

```
┌─────────────────────────────────────┐
│              HSM 内部                │
│                                     │
│  密钥生成 ──→ 密钥存储（加密区）       │
│      ↑               ↓              │
│      │         密码运算引擎           │
│      │         (AES/RSA/ECDSA...)   │
└──────┼──────────────┼───────────────┘
       │              │
   外部请求：       返回：
   "用这个密钥      密文/签名结果
    加密这段数据"   （明文密钥不出来）
```

应用程序只能发指令"用 Key-ID=42 签名这段数据"，**拿不到 Key-42 本身**。

#### 访问控制

- **多因素认证**：需要 PIN + 智能卡才能操作
- **M-of-N 机制**：例如需要 3 个管理员中的 2 个同时授权才能导出密钥
- **角色分离**：密钥管理员、审计员、操作员权限严格隔离

### 1.4 分类

```
按形态：
  PCIe 卡式 HSM  ─── 插在服务器主板上，高性能
  网络 HSM       ─── 独立设备，通过网络提供服务（Luna HSM, Thales nShield）
  USB HSM        ─── 便携，低成本（YubiHSM）
  云 HSM         ─── AWS CloudHSM, Azure Dedicated HSM（租用的专属硬件）

按认证级别（FIPS 140-2/140-3）：
  Level 1 ─ 基本算法正确性
  Level 2 ─ 防篡改涂层，需要身份认证
  Level 3 ─ 防篡改响应（检测到攻击自毁密钥）★ 大多数金融/政务要求
  Level 4 ─ 完整物理安全封装（军事/高安全场景）
```

### 1.5 典型应用场景

| 场景 | 具体用途 |
|---|---|
| PKI 根 CA | 根证书私钥存在 HSM 里，签发下级证书 |
| 支付系统 | PCI-DSS 要求 PIN 加密、交易签名必须用 HSM |
| 代码签名 | 软件发布私钥，防止被盗后签恶意软件 |
| TLS 卸载 | 服务器私钥在 HSM，Nginx/Apache 调用 HSM 做握手 |
| 数据库加密 | 列级加密密钥的"主密钥"托管在 HSM |
| KMS 底层 | AWS/GCP 的 KMS 底层就是 HSM 集群 |

## 二、三层密钥体系

### 2.1 整体结构

KMS 加解密服务中，密钥一般分为三层：

```
RootKey（HSM 内，永不离开硬件）
    ↓ 加密
  MK - Master Key（KMS 服务内）
    ↓ 加密
  DK - Data Key（业务系统内）
    ↓ 加密
  业务数据
```

### 2.2 根密钥 RootKey

- 作为整个体系的**信任根**，保存在 HSM 中
- RootKey **不会离开 HSM**
- 所有加解密操作通过 HSM 接口调用，HSM 只返回运算结果，不返回 RootKey 本身

### 2.3 主密钥 MK（Master Key）

- 起到**业务隔离**作用，推荐一个业务的一类数据使用一组 MK
- 位于 KMS 加解密服务内部，**不会暴露给业务系统**
- 以明文形式缓存在 KMS 进程内存中（用于实际加解密运算）
- 同时以加密形式（经 RootKey 加密后）持久化存储在 DB 中

#### 为什么需要在 DB 里存加密后的 MK？

明文 MK 是易失的（volatile），存在内存中，服务重启即丢失。DB 里的加密 MK 解决的是**持久化**问题：

```
KMS 服务重启 / 崩溃 / 扩容新实例
  → 内存清空，明文 MK 丢失
  → 从 DB 取出加密 MK
  → 调 HSM 解密 → 得到明文 MK
  → 重新缓存到内存，继续服务
```

#### DB 里加密 MK 的安全价值

加密 MK 保护的不是"KMS 自身"，而是**把不同攻击面隔离开**：

| 攻击场景 | 结果 |
|---|---|
| 攻击者只拿到 DB | 加密 MK 无法使用，需要 HSM 才能解密 ✅ |
| 攻击者只攻破 HSM | 没有 DB 里的加密 MK，无从下手 ✅ |
| 攻击者同时拿到 DB + HSM | 才能还原明文 MK ⚠️ |

### 2.4 数据密钥 DK（Data Key）

- 位于**业务系统内部**，实际加密业务数据
- 作用一：提升大文件的加解密性能（对称加密，本地运算，极快）
- 作用二：超高密级文件不需要传输到 KMS，可在本地加密，避免 KMS 管理员接触数据

## 三、信封加密

### 3.1 概念

信封加密（Envelope Encryption）是指：**用 MK 加密 DK，将加密后的 DK（eDK）和数据密文捆绑存储**，形如把开箱钥匙封入信封随箱存放。

> 不再使用 MK 直接加密数据，MK 只负责保护 DK，DK 负责加密数据。

### 3.2 与直接用 MK 加密数据的对比

**MK 直接加密数据：**

```
业务系统                        KMS
    │── 原始数据 ────────────→   │
    │                      用 MK 加密
    │← 密文 ─────────────────   │
```

每次加解密，原始数据都要进入 KMS。

**信封加密：**

```
第一步：申请 DK
业务系统                        KMS
    │── "给我一个 DK" ───────→  │
    │                      生成 DK，用 MK 加密得到 eDK
    │← 返回 (DK明文 + eDK) ──   │

第二步：本地加密，存储信封
    原始数据 + DK → 数据密文
    存储：[数据密文 | eDK]  ← 这就是"信封"
    DK 明文用完即丢弃

第三步：解密时，用 eDK 换回 DK
业务系统                        KMS
    │── eDK ────────────────→  │
    │                      用 MK 解密 eDK
    │← DK明文 ───────────────  │
    │
    │  本地：数据密文 + DK → 原始数据
```

### 3.3 优点

| 优点 | 说明 |
|---|---|
| 性能 | 大文件本地用对称 DK 加密，极快；只有 32 字节的 DK 需要走 KMS |
| 安全隔离 | 原始数据永远不进入 KMS，KMS 管理员无法接触业务数据 |
| 灵活性 | 不同数据可以用不同 DK，密钥轮换粒度更细 |

## 四、大规模场景下的加解密模式选型

### 背景

标准信封加密中，每次加解密都需要与 KMS 服务发生一次 RPC 交互。对于离线批量分析（如一次处理十几亿条数据），这种模式性能无法满足要求。

以下三种模式代表了**安全性与性能之间不同的权衡点**。

---

### 模式一：远程加解密（标准信封加密）

```
解密每条数据：取出 eDK → KMS RPC → 得到 DK → 解密
解密 10 亿条：→ 海量 KMS RPC，服务不可用
```

**适合场景**：C 端实时交易，单次请求量小，对安全性要求高

**缺点**：离线批量分析场景完全不可用

---

### 模式二：完全本地加解密

```
启动时：1 次 KMS RPC → 拿回 DK → 永久缓存在内存
之后：所有加解密全部本地完成，0 次 KMS 交互
```

**适合场景**：对性能要求极高，安全要求相对宽松

**核心问题：无法做密钥轮换**

```
DK 固定不变
  → 历史全量数据都用同一个 DK 加密
  → DK 一旦泄露
  → 所有历史数据全部暴露，且无法补救
```

固定 DK 还意味着密文分析攻击面更大——攻击者积累足够多的密文/明文对，破解概率更高。

---

### 模式三：近似本地加解密

**核心思路**：用时间维度切分 DK，把"无限多个 DK"变成"有限个可缓存的 DK"。

```
以 1 天为周期：
  Day1 的数据  →  用 DK-20240101 加密
  Day2 的数据  →  用 DK-20240102 加密
  ...

批量解密 1 年的数据：
  最多 365 个 DK → 最多 365 次 KMS RPC（懒加载，之后走缓存）
```

每条加密记录附带版本信息：

```json
{ "key_version": "20240101", "ciphertext": "..." }
```

解密逻辑：

```
读 key_version
  → 查本地缓存：有 DK-20240101？
      → 有：直接解密
      → 没有：去 KMS 换一次，缓存，然后解密
```

---

### 三种模式对比

#### 安全性：密钥泄露的"爆炸半径"

```
完全本地：  ████████████████████  全量历史数据
近似本地：  ███                   仅该时间窗口（1天/7天）
远程模式：  █                     仅该 DK 对应的少量数据
```

#### 性能：KMS 交互次数（解密 10 亿条、跨 1 年数据）

| 模式 | KMS 调用次数 |
|---|---|
| 远程模式 | ~10 亿次 |
| 完全本地 | 1 次（启动时） |
| 近似本地（按天） | ≤ 365 次 |
| 近似本地（按周） | ≤ 52 次 |

#### 密钥轮换能力

| 模式 | 轮换能力 |
|---|---|
| 完全本地 | ✗ 无法轮换 |
| 近似本地 | ✓ 按时间窗口自然轮换，旧 DK 可在保留期后撤销 |
| 远程模式 | ✓ 随时轮换，粒度最细 |

---

### 近似本地模式的残余问题

**① 时间窗口选择是安全与性能的博弈**

| 窗口粒度 | 优点 | 缺点 |
|---|---|---|
| 短（1 天） | 泄露影响范围小 | 缓存 DK 数量多，内存压力大 |
| 长（30 天） | 缓存 DK 少，内存友好 | 泄露影响范围更大 |

**② 多版本 DK 缓存的管理复杂度**

跨时间跨度的分析作业需要维护多版本 DK 缓存，对缓存失效策略和内存管理有额外要求。

**③ 缓存本身引入的风险**

DK 明文缓存在业务进程内存中，若进程被入侵（如内存 dump），可一次性拿走所有缓存的 DK。这是相比远程模式无法消除的残余风险。

---

## 五、总结

```
信任根
  RootKey（HSM）
    物理不可破，密钥永不以明文离开硬件
    ↓ 保护
  MK（KMS 内存 + DB 加密存储）
    内存中：实际运算用
    DB 中：持久化用，服务重启后恢复
    ↓ 保护（信封加密）
  DK（业务系统）
    实际加密业务数据
    ↓
  业务数据
```

**三种加解密模式的一句话定位：**

- **远程模式**：KMS 是守门人，每次都要过，安全最强，性能最差。
- **完全本地**：守门人只验证一次，之后形同虚设，性能最好，安全最弱。
- **近似本地**：守门人按时间段验证，缓存有效期内不重复敲门——在安全与性能之间找到工程上可接受的平衡点。

## 六、AES-GCM 加密算法

### 先拆开理解：AES + GCM

AES-GCM 是两部分的组合：

```
AES        →  底层块加密算法（加密引擎）
GCM        →  运作模式，决定 AES 怎么被使用
  ├── CTR mode   →  负责加密
  └── GHASH      →  负责认证（防篡改）
```

### 6.1 AES（块加密基础）

AES 是一个**块加密算法**，每次只能处理固定 128 bit 的数据块，密钥长度可选 128 / 192 / 256 bit。

直接用 AES 加密大文件有问题：
- 相同明文块 → 相同密文块（可被统计分析）
- 无法处理非 128 bit 整数倍的数据（需要 padding）

所以需要 GCM 这样的"运作模式"来解决这些问题。

### 6.2 CTR 模式：把块加密变成流加密

GCM 的加密部分使用 CTR（Counter）模式：

```
输入：Nonce（随机数） + Counter（递增计数器）
         ↓
      AES 加密
         ↓
      密钥流（KeyStream）
         ↓
      明文 XOR 密钥流 = 密文
```

```
┌─────────┬─────────┬─────────┐
│Nonce‖ 1 │Nonce‖ 2 │Nonce‖ 3 │  ← 计数器块（每块递增）
└────┬────┴────┬────┴────┬────┘
     │AES_K    │AES_K    │AES_K   ← 用密钥加密计数器
     ↓         ↓         ↓
  KS块1      KS块2      KS块3     ← 密钥流
     ↓ XOR    ↓ XOR    ↓ XOR
  明文1→密文1  明文2→密文2  明文3→密文3
```

**关键特性**：
- 每块加密**互相独立**，可以并行计算
- 不需要 padding（XOR 操作按实际长度来）
- 解密和加密是**同一个操作**（XOR 的对称性）

### 6.3 GHASH：认证标签（防篡改）

CTR 模式只解决了加密问题，但无法检测密文被篡改。GCM 引入了 **GHASH** 来生成一个认证标签（Auth Tag）：

```
┌─────────────────────────────────────┐
│  GHASH 的输入                        │
│  ① AAD（附加认证数据，只认证不加密）  │
│  ② 密文                              │
│  ③ 长度信息                          │
└──────────────────┬──────────────────┘
                   │ 在 GF(2¹²⁸) 伽罗瓦域上做乘法运算
                   ↓
              Auth Tag（128 bit）
```

最终存储/传输的内容：

```
┌──────────┬──────────────────┬─────────────┐
│  Nonce   │     密文          │  Auth Tag   │
│ (96 bit) │  (与明文等长)     │  (128 bit)  │
└──────────┴──────────────────┴─────────────┘
```

解密时，接收方重新计算 Auth Tag，与传输的 Tag 对比——**不一致说明密文被篡改，直接拒绝**。

### 6.4 AAD（附加认证数据）

GCM 可以认证**不需要加密的数据**，比如数据包头部、用户 ID、版本号等：

```
场景：加密消息体，但需要保证头部（路由信息）没被篡改

AAD = 消息头部（明文传输，不加密）
P   = 消息体（加密）

→ Auth Tag 同时覆盖 AAD 和密文
→ 任何一方被篡改，Tag 验证都会失败
```

### 6.5 核心特性汇总

| 特性 | 说明 |
|---|---|
| **认证加密（AEAD）** | 同时提供机密性 + 完整性 + 真实性，一个算法顶两个 |
| **高性能** | CTR 模式天然并行，现代 CPU 有 AES-NI 硬件指令加速，吞吐极高 |
| **无需 Padding** | 流加密方式，输出与输入等长 |
| **随机访问** | 可以直接解密任意位置的块，无需从头开始 |
| **在线加密** | 数据流式到来也可以处理，不需要提前知道全部数据 |

### 6.6 最大的坑：Nonce 不能复用

**同一个 Key + 同一个 Nonce，绝对不能加密两段不同的数据。**

如果 Nonce 复用，后果是灾难性的：

```
密文1 = 明文1 XOR AES(K, Nonce)
密文2 = 明文2 XOR AES(K, Nonce)

密文1 XOR 密文2 = 明文1 XOR 明文2

→ 攻击者拿到两段密文，XOR 一下就能得到两段明文的 XOR
→ 配合已知明文，可以还原另一段明文
→ 同时 GHASH 的认证密钥 H 也会泄露，Tag 伪造成为可能
```

**实践中的 Nonce 生成策略：**

| 策略 | 优点 | 风险 |
|---|---|---|
| 随机生成（96 bit） | 简单 | 数据量极大时（>2³² 条）有碰撞概率，需要轮换密钥 |
| 全局递增计数器 | 零碰撞概率 | 分布式场景下需要协调计数器 |
| 随机 + 计数器混合 | 兼顾两者 | 常见于 TLS 1.3 等协议 |

### 6.7 与其他模式的横向对比

| | AES-CBC | AES-CTR | AES-GCM |
|---|---|---|---|
| 加密 | ✅ | ✅ | ✅ |
| 完整性认证 | ❌（需额外 HMAC） | ❌ | ✅（内置） |
| 并行加密 | ❌（串行依赖） | ✅ | ✅ |
| 需要 Padding | ✅ | ❌ | ❌ |
| 随机访问解密 | ❌ | ✅ | ✅ |
| 硬件加速 | ✅ | ✅ | ✅ |
| 主要风险 | Padding Oracle 攻击 | 无认证，篡改不可检测 | Nonce 复用灾难 |

**AES-GCM 是目前最广泛使用的对称加密方案**，TLS 1.3、SSH、磁盘加密等场景均以它为默认算法，核心原因是：**一次操作同时搞定加密和认证，且性能极高**。

## 七、KMS 系统的核心技术挑战

### 7.1 高可用与容灾

KMS 是整个加密体系的信任根，一旦不可用，所有依赖它的服务都无法完成加解密操作——属于**全链路阻塞型故障**。

```
单机房：
  HSM 集群（主备 or 多活）
  → HSM 之间通过厂商私有协议同步密钥材料
  → 任意一台故障，其他节点无缝接管

跨地域：
  每个 IDC 部署独立 HSM 集群
  → RootKey 通过 HSM-to-HSM 安全通道跨域同步
  → 各地域 KMS 服务独立提供加解密，互不依赖
```

跨地域同步核心取舍：同步复制保证一致但增加延迟，异步复制保证可用但存在短暂不一致窗口。业内通常选择**异步复制 + 版本号对账**。

### 7.2 密钥轮换

密钥需要定期更换，但历史数据是用旧密钥加密的，轮换后必须能继续解密——**新旧密钥要共存过渡**。

**核心方案：密钥版本化**

```
MK 不是单一密钥，而是带版本的密钥序列：
  MK-v1（2024-01 创建，2024-06 退役）
  MK-v2（2024-06 创建，当前活跃）

每条加密数据附带版本标记：
  { "mk_version": "v1", "ciphertext": "..." }

解密时：读版本 → 用对应版本的 MK 解密
加密时：始终用最新活跃版本
```

**两种轮换策略：**

| 策略 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 立即重加密（Eager） | 轮换时批量用新密钥重加密所有旧数据 | 彻底，旧密钥可立即销毁 | 数据量大时任务可能跑几天 |
| 惰性重加密（Lazy） | 每次读取旧数据时顺手重写 | 平滑，无集中资源压力 | 旧密钥需保留更长时间 |

业内大多采用**惰性轮换 + 旧密钥保留期限制**（如 180 天）。

### 7.3 HSM 性能瓶颈

HSM 吞吐量有物理上限，但通过分层设计可以将其完全移出高频路径：

```
层次一：HSM 集群横向扩展，线性提升吞吐

层次二：减少 HSM 直接参与的操作
  HSM 只负责 RootKey 操作（加解密 MK）
  MK 操作（加解密 DK）在 KMS 软件层完成
  → HSM 请求量 = MK 数量级（百/千），而非业务请求量级（百万/亿）

层次三：MK 明文缓存
  MK 解密后缓存在 KMS 内存
  → 正常业务请求完全不触及 HSM
  → HSM 只在 KMS 启动/MK 轮换时被调用
```

### 7.4 RootKey 的冷启动与灾备恢复

**核心矛盾**：HSM 全部损毁时，RootKey 丢失 → 所有数据永久无法解密。但 RootKey 的备份本身不能用另一个密钥加密（否则无限递归）。

**方案：Shamir 秘密共享（SSS）**

```
将 RootKey 拆分成 N 份"碎片"，任意 K 份可以还原（例：5 份取 3）：

  RootKey ──SSS算法──→ 碎片1 → 管理员A（异地保险箱）
                        碎片2 → 管理员B
                        碎片3 → 管理员C
                        碎片4 → 法务部门托管
                        碎片5 → 银行金库

灾备恢复：召集任意 3 位管理员输入碎片 → 还原 RootKey → 导入新 HSM
```

单个碎片本身是无意义的随机数，持有者无法从中获得任何信息。这个流程业内称为 **Key Ceremony（密钥仪式）**，通常有公证人、录像、多方见证。

### 7.5 多租户密钥隔离

```
密钥命名空间隔离：
  每个租户有独立的密钥空间（Keyring）
  MK 归属于特定租户，跨租户访问直接拒绝

细粒度权限模型（类 IAM）：
  主体（用户/服务账号）对某个 MK 的某种操作
  例：
    service-A 可以用 MK-order 做 Encrypt + GenerateDataKey
    service-A 不能 Decrypt（只能加密，不能解密）
    audit-service 只能 DescribeKey（只读元数据）

硬件级隔离（高安全场景）：
  不同租户的 MK 存在不同的 HSM 分区（HSM Partition）
  物理上无法跨分区访问
```

### 7.6 密钥泄露的应急响应

当密钥疑似泄露时，撤销操作需要被所有缓存了该密钥的节点感知：

```
方案 A：短 TTL 缓存
  DK 缓存最多存活 5 分钟，自然感知撤销
  代价：每 5 分钟重新向 KMS 换一次 DK

方案 B：主动推送失效通知
  KMS 维护订阅关系，撤销时主动推送 invalidate
  实时生效，但实现复杂

方案 C：两者结合（业内主流）
  正常情况长 TTL，紧急撤销时主动推送 + 强制短 TTL
```

### 7.7 不可篡改审计日志

每一次密钥操作必须被记录，且日志本身不能被篡改：

```
方案 A：日志实时投递到独立系统
  操作日志实时写入独立日志服务（Kafka → S3）
  与 KMS 权限完全隔离，攻击者拿下 KMS 也无法修改已投递日志

方案 B：日志哈希链
  Log[n].hash = SHA256(Log[n].content + Log[n-1].hash)
  任何中间记录被篡改，后续所有哈希全部失效

方案 C：定期将日志哈希写入区块链或公开存证平台
  强化外部可验证性，适用于高合规要求场景
```

### 挑战全景总结

| 挑战 | 核心矛盾 | 主流解法 |
|---|---|---|
| 高可用容灾 | 可用性 vs HSM 硬件限制 | HSM 集群 + 跨地域异步复制 |
| 密钥轮换 | 新旧密钥共存过渡 | 版本化 + 惰性重加密 |
| HSM 性能瓶颈 | 吞吐需求 vs 硬件上限 | 密钥分层 + MK 缓存，HSM 退出高频路径 |
| RootKey 灾备 | 安全存储 vs 不能丢失 | Shamir 秘密共享 + Key Ceremony |
| 多租户隔离 | 共享平台 vs 权限隔离 | 命名空间 + 细粒度 IAM |
| 密钥泄露响应 | 实时撤销 vs 缓存一致性 | 短 TTL + 主动推送双保险 |
| 审计合规 | 完整记录 vs 防篡改 | 日志实时投递隔离系统 + 哈希链 |

## 八、业界典型 KMS 方案分析

> 以下内容来自各公司公开的技术博客、白皮书或开源代码，内部实现细节不保证完全准确。

### 8.1 AWS KMS

**最具代表性的商业 KMS，架构文档最完整。**

**密钥层次：**

```
HSM 集群（每个可用区独立）
    ↓
Domain Key（每个 HSM 域一个，HSM 内生成，不出硬件）
    ↓
CMK - Customer Master Key（用户创建的主密钥）
    ↓
Data Key（通过 GenerateDataKey API 下发给用户）
```

**值得关注的设计点：**

① **HSM Fleet 而非单机**：CMK 的密钥材料被加密分片后分散存储在多台 HSM 上，单台损毁不影响可用性。

② **CMK 永不离开 AWS 的 HSM 边界**：用户调用 `Encrypt` API 时数据进入 AWS 加密，永远拿不到 CMK 明文，有第三方审计报告背书（FIPS 140-2 Level 3）。

③ **三种 CMK 类型满足不同合规需求：**

```
AWS Managed Key      → AWS 自动管理轮换，用户无感
Customer Managed Key → 用户控制轮换周期、访问策略
CloudHSM Key         → 密钥材料存在用户自己租用的独占 HSM 里
External Key (XKS)   → 密钥材料存在用户自己机房，AWS 每次加解密都回调用户的 HSM
                       （2022 年推出，解决"不信任 AWS"的合规场景）
```

④ **审计强制绑定 CloudTrail**：所有密钥操作自动留审计日志，用户无法关闭。

### 8.2 HashiCorp Vault

**开源界最主流的密钥管理方案，架构完全公开。**

**最有特色的设计：Seal/Unseal 机制**

Vault 启动时处于 Sealed（封印）状态，所有数据均为密文，自身也不持有解密密钥。必须经过 Unseal 才能提供服务：

```
初始化时：
  生成 Master Key → Shamir 拆分成 N 份（默认 5 份，3 份可还原）→ 分发给不同管理员

每次重启：
  K 个管理员各自输入碎片 → 还原 Master Key → 解密存储 → 服务可用
```

**Transit Secrets Engine（等同于 KMS 核心功能）：**

```
POST /transit/encrypt/my-key  plaintext: "hello"
→ 返回 ciphertext: "vault:v2:abc123..."   ← v2 是密钥版本号

POST /transit/decrypt/my-key  ciphertext: "vault:v2:abc123..."
→ 返回 plaintext: "hello"
```

轮换后旧版本密文仍可解密，新加密自动用新版本——**版本化轮换开箱即用**。

**Auto Unseal（工程实用化的妥协）：**

手动 Unseal 在生产环境很麻烦，Vault 支持把 Master Key 托管给云 KMS 自动解封：

```
Vault 启动 → 调 AWS KMS 解密 Master Key → 自动完成 Unseal
```

这形成一个有趣的**嵌套信任**：Vault 依赖 AWS KMS 保护自己的根密钥，而业务又依赖 Vault 做密钥管理。

### 8.3 美团 KMS

**公开来源：美团技术团队博客（2021-2022 年）**

**整体架构：**

```
业务系统
    ↓ 调用 SDK（内嵌在业务进程里）
KMS Client SDK
    ↓ RPC
KMS Server（负责 MK 管理、DK 下发）
    ↓
HSM（保护 RootKey）+ DB（存储加密后的 MK）
```

SDK 内嵌是美团的特色设计——加解密逻辑封装在 SDK 里，业务方接入成本极低，SDK 负责 DK 的本地缓存和版本管理。

**针对离线大数据场景：近似本地加解密**

按时间窗口（1 天/7 天）复用 DK，把"无限多个 DK"变成"有限个可缓存的 DK"，将 KMS RPC 次数从亿级降至百级（详见第四章）。

**数据库字段级加密的盲索引问题：**

字段加密后 `WHERE field = ?` 查询失效（密文不能直接比较）。解法：

```
额外存一份"盲索引"：
  blind_index = HMAC(field_value, 独立的索引密钥)

查询时：
  WHERE blind_index = HMAC(query_value, 独立的索引密钥)
```

HMAC 单向，索引密钥与加密密钥隔离，索引泄露也无法还原原始数据。

### 8.4 Cloudflare Keyless SSL

**一个"密钥不出客户机房"的独特方案。**

**背景问题：** 大企业（如银行）把业务托管给 Cloudflare 做 CDN/DDoS 防护，但合规要求 TLS 私钥必须留在自己机房。

**解法：**

```
正常 TLS 握手：
  客户端 → Cloudflare 边缘节点 → 用私钥完成握手

Keyless SSL：
  客户端 → Cloudflare 边缘节点
           → 将需要私钥运算的部分转发给客户的 Key Server（在客户机房）
           ← Key Server 完成签名/解密，返回结果
           → Cloudflare 用结果完成握手

私钥永远在客户自己的 Key Server 里，Cloudflare 只拿到运算结果。
```

本质上是把 HSM 的"不出境"原则扩展到了**跨公司边界**，代价是每次 TLS 握手多一次跨网络 RPC（Cloudflare 工程博客称将延迟控制在了几毫秒以内）。

### 横向对比

| | AWS KMS | HashiCorp Vault | 美团 KMS | Cloudflare Keyless |
|---|---|---|---|---|
| **定位** | 云托管服务 | 自建开源方案 | 企业内部平台 | 密钥不出境方案 |
| **RootKey 保护** | AWS 自有 HSM Fleet | Auto Unseal 托管给云 KMS | HSM | 客户自有 Key Server |
| **最大亮点** | External Key Store（完全不信任 AWS 场景） | Seal/Unseal 机制工程化 | 近似本地加解密解决大数据场景 | 私钥跨公司边界不出境 |
| **适用场景** | 上了 AWS 的业务 | 多云/自建机房 | 大规模 C 端 + 数据仓库 | CDN/代理场景下的合规 |
| **公开程度** | 架构文档完整，代码不开源 | 完全开源 | 技术博客部分公开 | 协议设计公开，代码部分开源 |

> 如做 KMS 选型或自研，最值得深读的是 **Vault 的开源代码**（Transit Engine 部分）和 **AWS KMS 白皮书**，分别代表"开源自建"和"云托管"两个方向最成熟的工程实践。
