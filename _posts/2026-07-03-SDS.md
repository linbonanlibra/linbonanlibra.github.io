# Redis SDS（Simple Dynamic String）技术笔记

---

## 一、为什么不直接用 C 字符串？

```c
char *s = "hello";  // C 原生字符串
```

| 问题 | 原因 |
|---|---|
| 获取长度 O(N) | 需要遍历到 `\0` 才知道长度 |
| 不安全 | `strcat` 等操作不检查缓冲区边界，容易溢出 |
| 不支持二进制数据 | 遇到 `\0` 就认为字符串结束，无法存图片、序列化数据等 |
| 频繁 realloc | 每次追加都需要重新分配内存 |

---

## 二、SDS 的数据结构

```c
struct __attribute__ ((__packed__)) sdshdr8 {
    uint8_t  len;    // 已使用长度
    uint8_t  alloc;  // 总分配长度（不含 header 和 \0）
    uint8_t  flags;  // 低3位标识 header 类型
    char     buf[];  // 实际数据
};
```

内存布局：

```
+-----+-------+-------+---+---+---+---+---+---+
| len | alloc | flags | h | e | l | l | o | \0|
+-----+-------+-------+---+---+---+---+---+---+
 ←── header ──→        ←────── buf[] ──────────→
                        ↑
            对外暴露的指针指向这里（兼容 C 字符串）
```

> 对外暴露的是 `buf` 的指针，因此 SDS 可以直接传给 C 标准库函数，完全兼容。

---

## 三、五种 header 类型

Redis 根据字符串长度自动选择合适的 header，节省内存：

```c
struct sdshdr5  { ... }  // 长度 < 32，len 直接编码在 flags 里
struct sdshdr8  { ... }  // 长度 < 256，  len/alloc 各占 1 字节
struct sdshdr16 { ... }  // 长度 < 65536，各占 2 字节
struct sdshdr32 { ... }  // 各占 4 字节
struct sdshdr64 { ... }  // 各占 8 字节
```

## 四、核心特性

### 1. O(1) 获取长度

```c
// C 字符串：O(N)，需要遍历到 \0
strlen("hello");

// SDS：O(1)，直接读 header 字段
sds->len;
```

### 2. 预分配策略（追加时多分配，减少 realloc）

```c
// Redis 源码中的扩容逻辑（简化）
if (new_len < 1MB) {
    new_alloc = new_len * 2;   // 小于 1MB：分配两倍所需空间
} else {
    new_alloc = new_len + 1MB; // 大于 1MB：每次多分配 1MB
}
```

图示：

```
追加 " world" 后（new_len=11）：

[len=11 | alloc=22 | flags | h e l l o   w o r l d \0 |  预留空间  ]
                                                          ↑ 下次追加无需 realloc
```

### 3. 惰性空间释放

字符串缩短时，**不立即释放内存**，只更新 `len`，多余空间留着备用：

```c
// "hello world" 截断为 "hello"
s->len = 5;  // 只改 len，alloc 仍然是 11
// 内存保留，下次追加可直接复用
```

### 4. 二进制安全

以 `len` 判断长度，而非 `\0`，因此内容中可以包含任意字节：

```
C 字符串： h  e  l \0  o  → 认为到 \0 结束，长度=3（数据截断！）
SDS：      h  e  l \0  o  → len=5，完整保留，长度=5
```

这使得 Redis 可以存储图片、音频、序列化对象等任意二进制数据。

## 五、哪些上层结构依赖 SDS？

几乎所有 Redis 数据类型都用到了 SDS，但角色不同：

| 数据结构 | 依赖 SDS 的地方 |
|---|---|
| **String** | 值本身直接存为 SDS |
| **Hash** | hashtable 编码下，field 和 value 都是 SDS |
| **List** | quicklist 节点中的字符串元素 |
| **Set** | hashtable 编码下，每个 member 是 SDS |
| **Zset** | skiplist 编码下，member 是 SDS |
| **所有 Key 名称** | Redis 的 key 本身就是 SDS |

Redis **内部**也使用 SDS（复用其动态扩容能力）：

```c
// server.h
struct redisServer {
    sds aof_buf;   // AOF 写入缓冲区
};

typedef struct client {
    sds querybuf;  // 客户端输入缓冲区
} client;
```

## 六、为什么 SDS 需要追加/预分配特性？

### 直接动机：面向用户的 APPEND 命令

```
APPEND key "hello"
APPEND key " world"
APPEND key "!"
```

String 作为通用值类型，需要支持原地动态修改，预分配能减少 realloc 次数。

### 顺带受益：内部缓冲区复用

AOF buffer 和客户端 querybuf 也是 SDS，但这更多是**复用现有工具**，而非 SDS 设计追加特性的原始驱动力：

```
SDS 设计追加特性  ← 主要因为 String 类型本身需要支持动态修改
AOF buffer 选用 SDS ← SDS 的能力恰好满足需求，顺手复用
```

## 七、与 listpack 的分配策略对比

| | SDS | listpack |
|---|---|---|
| 分配策略 | 预分配（容量翻倍 / +1MB）| 精确 realloc |
| 内存占用 | 略有预留空间 | 零浪费 |
| 追加性能 | 均摊 O(1) | 每次可能拷贝 |
| 适用场景 | 持续追加、频繁修改的字符串 | 元素少、写入稳定的小数据集 |

> **核心原则：数据的变化模式决定分配策略。** 追加频繁就预分配，写入稳定就精确分配。

---

## 八、总结对比

| 特性 | C 字符串 | SDS |
|---|---|---|
| 获取长度 | O(N) | O(1) |
| 缓冲区安全 | ❌ | ✅ 自动扩容检查 |
| 二进制安全 | ❌ | ✅ |
| 追加性能 | 每次 realloc | 预分配，均摊 O(1) |
| 缩短时内存 | 立即释放 | 惰性释放，保留备用 |
| 兼容 C 函数 | ✅ | ✅（buf 指针直接兼容）|
